## Problem 9.1 — Finance module visible to non-admin staff by default *(owner's issue #1, first half)*

**Root cause:** `BottomNav.tsx`'s `NAV_ITEMS` marks the Finance entry `guardianHidden: true` only — there is no equivalent `staffHidden`/permission-based condition, so every `actorType === 'staff'` account sees the tab regardless of role. `App.tsx`'s `tab === 'finance'` branch confirms the same gap at the routing layer: the only actor-type check present routes guardians/students to `GuardianPortal`'s fees tab; every other staff member — admin or not — falls through to `<FinanceModule schoolId={schoolId} isAdmin={isAdmin} intent={intent.intent} schoolType={schoolType} />` with no permission check at all. `FinanceModule.tsx` itself already has real, live `finance.*` permission keys wired into its **write** actions (`finance.fees.manage`, `finance.payments.record`, `finance.discounts.apply` — converted in PRD Session 10) — but nothing gates **entry into the module at all**. A non-admin teacher with zero finance permissions currently reaches the same read-heavy Balances/Assignments/Fee Heads screens as a bursar would, with only the write buttons hidden.

**Owner clarification (2026-07-23):** module entry should be gated on **admin-role OR holding any `finance.*` permission** — not admin-only. A non-admin bursar/accountant role that holds e.g. `finance.fees.manage` or `finance.payments.record` must still be able to open the module; only a non-admin staff member holding **zero** finance permissions should be blocked from entry entirely. This matches the codebase's own existing "union of granted permissions" convention (`authStore.can()`, per §3.7) rather than inventing a new access model.

**Master plan sections to observe:** §3.7 (permissions are unioned across held roles; no hardcoded role name ever gates anything), §7.3 (`permissions`/`role_permissions`/`staff_roles` — the catalog already has the six live `finance.*` keys this fix reads, no new keys needed for entry itself), §3.2 (RLS is the real backstop; a UI gate alone is not sufficient — see Goals below).

**Files touched:**
- `src/components/BottomNav.tsx` — `NAV_ITEMS`'s Finance entry needs a real visibility predicate, not a static boolean. `getVisibleNavItems()` currently takes `actorType` and (separately) `canViewStudents` as a bolted-on special case for Students — Finance needs the same treatment: a `canViewFinance` boolean threaded in from the caller (computed via `useAuthStore`'s `can()` against all six `finance.*` keys, OR'd with `isAdminRole`), not a second identity query.

Pull the live RLS policies for every table `FinanceModule.tsx` reads from (`fee_heads`, `fee_assignments`, `payments`, `fee_discounts`, `installment_plans`) via the SQL query in Goal 1 of the Definition of Done below — confirm whether read access is currently school-boundary-only (meaning any staff member can read finance data at the DB layer regardless of the new UI gate) before deciding whether a DB-layer fix is also required this session or can be tracked as a fast-follow.

## Problem 9.2 — Finance analytics/balance-summary card has no permission gate *(owner's issue #1, second half)*

**Root cause:** `FinanceModule.tsx`'s `renderBalances()` computes `totalBalance`/`totalPaid`/`totalAssigned`/`outstanding` and renders them inside `.fin-balance-summary` unconditionally — the block sits above the searchable student list with no `isAdmin`/`can()` check of any kind. Any staff member who clears Problem 9.1's entry gate (including a non-admin bursar holding only, say, `finance.payments.record`) currently sees full school-wide fee totals, not just the slice relevant to their own actions.

**Owner clarification (2026-07-23):** this card should be **hidden completely unless the viewer holds an explicit permission** — not shown in a reduced/personal form, and not unlocked by the same keys that unlock module entry. The owner explicitly chose a **brand-new permission key** (`finance.analytics.view`) over reusing `finance.fees.view` or `finance.reports.view`, so that a bursar who can record payments and manage fee heads does not automatically see school-wide totals unless separately granted. Enforcement should follow best practice: a UI gate for responsiveness, backed by the real RLS/DB layer as the actual boundary — matching this project's own §3.2 discipline ("RLS is the single point of failure," the UI gate is a convenience, never the only lock).

**Master plan sections to observe:** §3.7 (new permission keys are a one-row `permissions` insert plus `role_permissions` wiring, never a schema change — the exact convention already used for e.g. `hr.leave.types_manage`'s proposed-but-not-yet-inserted precedent), §7.3 (catalog shape: `id, key, module, description`), §3.2 (RLS as the real backstop — this card's underlying data (aggregated payment/fee totals) has no dedicated table of its own to attach RLS to directly, since it's a client-side `reduce()` over `StudentBalance[]` already fetched for the list below it; the real gate here is arguably "don't fetch/expose the aggregate at all to an unpermitted caller" at the query layer, not just hide the rendered card — see Goals below).

**Files touched:**
- **New migration:** `insert into permissions (key, module, description) values ('finance.analytics.view', 'finance', 'View school-wide fee/payment totals and outstanding-balance summary');` — a one-row insert, same shape as every other catalog addition in this project's history, run in the same migration as Problem 9.1's RLS work if that turns out to be needed.
- `src/routes/FinanceModule.tsx` — `renderBalances()` gains a `canViewAnalytics = can('finance.analytics.view') || isAdmin` check (read in-component via `useAuthStore`, matching every other module's own conversion pattern from Session 10 — no prop threading), wrapping only the `.fin-balance-summary` block. The student list itself, and `fin-count` line beneath it, are unaffected — this problem is scoped to the aggregate card only, per the owner's own scoping.

**Goals before moving on:**

**Final confirmation step surfaced a test-setup mix-up, not a further code defect — traced to ground truth before concluding anything:** owner reported the analytics-only holder still saw the lock screen after the fix above shipped. Direct SQL against `staff`/`staff_roles`/`role_permissions` for the actual test account (`abdulkarim@mc.test`, found via a `staff` listing after two earlier email guesses returned zero rows) showed the "Test finance" role granted exactly one key — `finance.reports.view`, not `finance.analytics.view` — confirming the lock screen was correct behavior for the permission actually held, not a bug. A follow-up report that the checkbox for `finance.analytics.view` was missing from the Settings roles UI entirely was also traced to ground truth rather than assumed: `select key from permissions where key = 'finance.analytics.view'` confirmed the row genuinely exists, `loadPermissionsCatalog()` was confirmed to run a plain unfiltered `select` with no exclusion, and a fresh on-device screenshot (post-migration, post-hard-refresh) confirmed the checkbox does render correctly, in the correct position, in the live catalog's order — the row had simply been visually adjacent to and confused with "View financial summary reports" (`finance.reports.view`) during manual role-editing. **One further, real, but separately-scoped bug was found while tracing this — logged, not fixed in this pass:** `SettingsModule.tsx`'s roles-tab `load()` fetches `loadRoles()` and `loadPermissionsCatalog()` in parallel via `Promise.all`, but its early-return guard (`if (rRes.error) { ...; return }`) only checks the *roles* fetch's error — if `loadPermissionsCatalog()` ever fails while `loadRoles()` succeeds, `setCatalog()` is silently never called and the permissions list would go stale or empty with no visible error, since only the roles-fetch failure path surfaces `error` to the UI. Did not end up being the cause of anything in this session (both fetches were succeeding throughout), but is a real defect independent of everything else here — flagged for a future pass rather than bundled into this one.

## Problem 9.3 — Non-admin staff addressed by role word instead of first name; profile card incomplete

**Root cause:** Four separate sites across the app derive a display name the same fragile way:
```
const staffName = (session?.user?.user_metadata?.full_name as string | undefined) ?? 'Teacher';  // TeacherDashboard.tsx:364
const staffName = (session?.user?.user_metadata?.full_name as string | undefined) ?? 'Admin';     // AdminDashboard.tsx:200
{(session?.user?.user_metadata?.full_name as string | undefined)?.[0]?.toUpperCase() ?? '•'}       // App.tsx:709 (header chip avatar initial)
{(session?.user?.user_metadata?.full_name as string | undefined) ?? session?.user?.email ?? '—'}   // App.tsx:774 (account popover name)
```
`user_metadata.full_name` is a Supabase **Auth** field, set only if something explicitly wrote it at signup — it is not guaranteed to be populated for staff accounts provisioned server-side (e.g. via the `create-staff-account` Edge Function), and `authStore.ts`'s `resolveIdentity()` never fetches the real `staff.full_name`/`students.full_name` column at all, despite that column existing, being `not null`, and already being `[STD]`-readable by any staff member (confirmed via the master plan's schema section — no admin restriction on `staff.full_name`/`staff.email`). When `user_metadata.full_name` is unset, the two dashboard files fall back to the **literal words "Teacher"/"Admin"** as if they were real names — producing "Good morning, Teacher" instead of the person's actual first name. This is not a display-formatting bug; it is a wrong data source with a literal-string fallback standing in for a name.

**Owner clarification (2026-07-23):** resolve the real name from the `staff`/`students` table (best practice — a single reliable source of truth, resolved once at login alongside `isAdminRole`, not re-derived per-screen from auth metadata). Scope is limited to surfaces showing the **signed-in person's own name** (header chip, greeting, account popover) — not an audit-trail-wide rename of every "posted by"/"marked by" site elsewhere in the app, which the owner confirmed is out of scope for this fix. Profile card fields: full name, email, and role at minimum, informed by standard mobile-app account-card conventions (see Goals below) rather than guessed ad hoc.

**Master plan sections to observe:** §3.2 (`staff`/`students` RLS is `[STD]` — no new RLS needed, this is a read the caller is already permitted to make), §7.2 (`app_identities.actor_record_id` — the same join `authStore.ts`'s `resolveAdminRole()` already performs to get from an auth session to a real `staff.id`; the name fetch should ride the same round trip, not add a second one), §5 (business logic in service files, Zustand only for cross-cutting state — `authStore.ts` is exactly the right place for this, matching where `isAdminRole`/`permissionScopes` already live).

## Problem 9.10 — Manually assigned matric serial number incorrectly blocks/absorbs every lower number

**Root cause:** Confirmed directly against the live `set_matric_number_manual()` function body (via `information_schema.routines`). The function's uniqueness check is:
```sql
select current_value into v_current_counter_value
from matric_sequence_counters
where school_id = p_school_id
  and admission_year = p_admission_year
  and counter_key = coalesce(v_counter_programme_id, '00000000-0000-0000-0000-000000000000'::uuid)
for update;

if v_current_counter_value is not null and v_current_counter_value >= p_sequence_number then
  raise exception 'Sequence number % has already been used ...';
```
`matric_sequence_counters.current_value` is a **high-water mark** — the highest sequence number ever handed out or manually set for a given scope+year — not a record of which individual numbers were actually issued. The check above conflates two different questions: "is this exact number already assigned to a real student" (the question that matters) against "is this number less than or equal to the counter's current position" (what the code actually asks). Manually assigning 70 correctly fast-forwards the counter (`insert ... on conflict ... do update set current_value = greatest(current_value, excluded.current_value)`, further down in the same function) so future autogeneration correctly continues from 71 — that part of the design is sound. But because the `>=` check runs **before** the real, correct, identity-based check further down in the function (`select ... from students where matric_number = v_result`, kept today only as a secondary safety net for formatted-string collisions), every number 1–69 now permanently fails the position check and is reported as "already used," regardless of whether any of them were ever actually assigned to a student. The function's own inline comment ("the actual fix: check the counter, not a formatted string") shows this was already patched once, in the wrong direction — the fix moved the check onto the counter's position instead of onto real student data, which is the inverse of what a uniqueness check should verify.

**Root cause confirmed safe on the concurrency side:** the `for update` lock is scoped to the correct row (`school_id`, `admission_year`, `counter_key`) — the same row a concurrent manual entry for the same scope+year would also need to touch — and is not tied to the buggy `>=` comparison. Removing the comparison while keeping the lock does not reopen any race window; two staff manually entering the same number at the same moment are still serialized by the row lock, and the pre-existing unique index on `students.matric_number` (SESSION 55) remains as a hard, final backstop against a true collision either way.

**Owner clarification:** a **permanent** fix is required, not a temporary patch — explicitly rejecting any option that could later re-fail under load, concurrency, or repeated use. Confirmed scope: the false-positive blocking of numbers below a manually-set high point is the actual bug to close; gap-filling (autogeneration later reclaiming skipped low numbers on its own) is a separate, not-yet-decided product question, not assumed in scope for this fix.
